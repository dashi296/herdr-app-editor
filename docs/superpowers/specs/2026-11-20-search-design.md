# 行を指定して開く・プロジェクト全体の文字列検索 設計

日付: 2026-11-20 / 対象: Herdr Editor（`editor/`）

## 目的と理由

Herdr Editor ではファイル名で開くことはできるが、「この文字列がどこにあるか」から開くことができない。エディタでよく使う「プロジェクト全体を検索して、該当の行へ飛ぶ」をできるようにする。土台として、editor に「ファイルを開いて指定した行へ移動する」機能を足す。この土台は、後で端末に出た `file:line` から開く機能にも使える。

スパイク S12（`docs/spikes/2026-11-20-s12-jump-to-line.md`）で、`EditorState.set_selected_range` が選んだ位置まで表示を動かすことを確かめた。Herdr に変更は要らない。

## 目標

1. editor が、開くファイルと一緒に行（と列、選ぶ文字数）を受け取り、ファイルを開いたらその位置を選択して表示する。
2. 新しいポップアップ（文字列検索）で文字列を入力すると、ファイル検索と同じフォルダの中の一致する行が並び、選ぶとその行で開く。
3. 開き方はファイル検索と同じにする。Enter はタブの editor で開き、なければ新しい pane を開く。cmd-Enter（Linux / Windows は ctrl-Enter）とクリックの修飾キーは、常に新しい pane で開く。

## 目標外

- ファイル内検索（cmd-f）。S12 で作れることは分かっているが、今回は作らない。
- 置換（一括置換を含む）。
- 正規表現での検索。今回は文字列そのままの一致だけにする。
- 端末に出た `file:line` を開く操作。土台だけ作り、入口は作らない。
- Files パネルから行を指定して開くこと。

## 失敗とみなすこと

- 大きなフォルダ（`~` など）で検索してウィンドウが固まる、または結果が出ないまま終わらない。
- 未保存の編集があるファイルの検索結果を選んだとき、編集が失われる、または保存の確認が出て邪魔になる。
- 導入の手順が、ファイル検索のときより分かりにくくなる。

## 制約

- Herdr Desktop 0.1.16。ファイル検索の制約（S10 / S11）をそのまま受ける。オーバーレイから pane を作らないこと、`props()` は `init()` で読むこと。
- オーバーレイの形は mod ごとの `mod.json` で決まり、`mod.open` は mod の名前しか受け取らない。そのため、別のポップアップには別の mod が要る。
- 名前は `src/core/names.ts` に置く（RECIPE の名前の衝突ルールと同じ）。

## 進め方の候補

| 候補 | 内容 | 判断 |
|---|---|---|
| A（採用） | editor に行の指定を足し、その上に文字列検索のポップアップを作る | 利用者が選んだ |
| B | ファイル内検索（cmd-f）を先に作る | editor の中で完結するが、プロジェクト全体を探す用途に答えない |
| C | ファイル検索のポップアップを1つにまとめ、`:` で行へ移動、`#` で文字列検索と切り替える | キーが1つで済むが、入力の決まりを覚える必要があり、ファイル検索の動作も変わる |

A の中で、文字列検索をファイル検索と同じポップアップのモードにするか、別の mod にするかは、こちらで別の mod にした（下記「決めたこと」）。

## 決めたこと

### 1. 行を指定して開く（editor）

- `open` コマンドと、新しい pane の props に、省略できる `at` を足す。`at` は `{ line, col?, len? }` で、`line` と `col` は 1 から数える。`col` と `len` は UTF-16 の単位（`EditorState` のオフセットと同じ）。`git grep --column` が返す列はバイト単位（`あいう foo` の `foo` は 11）なので、文字列検索の側で一致した行の内容から UTF-16 単位に直してから渡す。`at` がない要求は今までと同じに動く。
- ファイルを読み込み、`EditorState` に内容を入れた後で、`line` 行目の `col` 文字目から `len` 文字を `set_selected_range` で選び、editor に focus する。`col` がなければ行頭、`len` がなければ選択なし（カーソルだけ）。`line` が行数を超える場合は最終行にする。`col` と `len` が行からはみ出す場合は、行の中に収める。
- **同じファイルへの要求は、読み直さずに移動だけする。** 今の editor は、同じファイルへの `open` でも、未保存の編集があると保存の確認を出す。`at` を伴う同じファイルへの要求は、確認を出さず、読み直しもせず、未保存の編集を残したまま移動する。
  - 行番号はディスク上の内容から求めたものなので、未保存の編集で行がずれている場合は、ずれた行へ移動する。これは受け入れる。
  - `at` のない同じファイルへの要求は、今までどおりの動作にする。
- 下書きの復元（Restore draft）を案内する場面では、移動を先に行い、案内はそのまま出す。
- 開けないファイル（1 MiB 超、UTF-8 でない、NUL を含む）は、今までどおりメッセージを出し、移動はしない。

### 2. 文字列検索のポップアップ（新しい mod）

- **mod:** `herdr-app-editor-search`（`editor/mods/` の下）。`mod.json` はファイル検索と同じ形（`popup`、`at: top`、`focusable: true`）にする。
- **キー:** 導入時に聞く。既定の案は `cmd-shift-f`（VS Code、Zed、JetBrains の「Find in Files」）。RECIPE の「キーを聞く」手順を、ファイル検索と合わせて1回の確認にまとめる。Linux / Windows は `ctrl-shift-f` を案として、同じ注意（修飾キーなしの `ctrl-<文字>` を避ける）を書く。
- **探すフォルダ:** ファイル検索と同じ（`currentLocation()`。editor にフォーカスがあるときは同じタブの端末のフォルダ）。開くタブも、ファイル検索と同じく開いたときのタブ。
- **探し方:**
  - Git のリポジトリでは `git grep -n -I --column --no-color -F -e <query>` を使う。ignore されたファイルは探さず、追跡していないファイルは `--untracked` で含める（ファイル検索が `ls-files -co` で追跡外を含むのに合わせる）。
  - それ以外では `grep -rnI -F --exclude-dir=.git --exclude-dir=node_modules -e <query> .` を使う。`grep` には列番号がないので、`col` は自分で求める。
  - 大文字と小文字: 入力がすべて小文字なら区別しない（`-i`）。大文字を含むなら区別する（smart case）。
  - 2文字以上で検索する。入力が止まってから 250 ms 後に実行する。前の検索がまだ動いていたら、その結果は捨てる。
  - 時間制限は 10 秒（ファイル検索と同じ）。結果は 500 件までで打ち切り、打ち切ったことを表示する。1行は表示のために 200 文字で切る。
  - 結果を出す `exec` には `cwd` と `on`（別のマシン）を渡す。別のマシンでも同じコマンドで動く。
- **表示:** 1行に `path:line` と、一致した行の内容（前後の空白を除く）を並べる。一致した部分の強調は、できれば行う（細部は作る人に任せる）。上下キーで選び、Enter で開く。Esc で閉じる。状態の表示（「Searching…」「No matches.」「Cannot search this folder: …」「Type at least 2 characters.」）はファイル検索に合わせる。
- **開き方:** ファイル検索と同じ。タブに editor があれば `open` コマンドに `at` を付けて送る。なければ、ファイル検索の `SPLIT_SCRIPT` で後から pane を分割し、props に `at` を付ける。`SPLIT_SCRIPT` は2つの mod で共有する。待つ対象のオーバーレイ名は、引数で渡しているので変える必要はない。

### 3. 導入・ドキュメント

- `editor/RECIPE.md` に、文字列検索の mod、キー、`at` の動作、Done when の項目を足す。「Tell the person」の1行に、`git grep` と `grep` を足す。
- `editor/keys.json` に既定のキーを足す。
- README の一覧の説明に、文字列検索を足す。
- herdr.dev の説明文（RECIPE の最初の段落）に1文足す。

### 4. 設計の確認で出た点（こちらで決めたこと）

- **同時に動く検索は1つまで。** `exec` は途中で止められず、出力は 8 MiB で切られる（`types/herdr.d.ts`）。検索が動いている間に入力が変わったら、最新の入力だけを覚えておき、今の検索が終わってから実行する。途中の入力は捨てる。前の結果は、新しい入力と一致しない限り表示しない。`sh -c '… | head'` での打ち切りは、`sh` に頼ることになるので使わない。
- **時間切れと出力の上限では、得られた分を表示する。** ファイル検索が `find` の失敗でも出力を使うのと同じにする。`exec` が時間切れで結果を返す場合は、`stdout` を解釈して「Stopped after 10 s: showing what was found」を出す。例外を投げる場合は「Cannot search this folder: …」にする。実機で確かめた結果、`exec` は時間切れで例外を投げ、途中の出力は返さない（trial7）。したがって時間切れでは「Cannot search this folder: …」になる。出力の最後の行が途中で切れている場合は、その行を捨てる。
- **`set_selected_range` の単位は UTF-16。** `gpui-kit.d.ts` の `selected_range()` に「UTF-16 offsets」とある。S12 の記録は PR #32 にある（`docs/spikes/2026-11-20-s12-jump-to-line.md`）。新しい pane の場合、表示前に選択して画面が動くかは確かめていない。読み込み直後に選択し、実機で動かなければ、最初の描画の後にもう一度選択する。
- **editor が待機中でないときに、同じファイルへの `at` が届いた場合:**
  - 別のファイルの保存確認が出ているとき: 今の `handleOpen` と同じく、その確認を閉じて取り消し、移動する。
  - そのファイルを読み込み中のとき: 最後に届いた `at` を覚えておき、読み込みの後に使う。
  - 再起動したとき: `at` は1回だけ使う。再起動後は、保存した pane の状態どおりにファイルを開き、`at` は使わない。

## 作る人に任せること

- `at` の受け渡しの内部の形（コマンドの JSON の中の置き場所。今の `open` の JSON に足す形が自然）。
- `git grep` と `grep` の出力の解釈と、テストの分け方（`src/core/` に純粋な関数として置き、`quick-open/match.ts` の形に合わせる）。
- 結果の行の見た目の細部。ファイル検索の行（28 px、`truncate`）に合わせる。
- `grep` が使えない環境（Windows）での扱い。今のファイル検索と同じく、エラーを表示すればよい。

## 確かめ方

- 単体テスト: `at` の範囲計算（行数・行の長さの超過、CRLF、UTF-16 のサロゲートペア）、`git grep` と `grep` の出力の解釈、smart case の判定、同じファイルへの要求の扱い（ルーティング）。
- UI テスト（`tests/ui/`）: 文字列検索ビューの入力・遅延・古い結果の破棄・開き方。editor の `at` 付き `open`。
- 実機: 検索して開く、同じファイルの別の行へ移る（未保存の編集あり）、新しい pane で開く、大きいフォルダでの打ち切り。
