# スパイク結果: S6（watchFolder とポーリングのコスト）

実施日: 2026-11-16 / 環境: macOS、Herdr Desktop 0.1.15 / スパイク: `spikes/s6-watch/`、ログ: `docs/spikes/s6-logs/result.json`

検証用の Mod を overlay で一度だけ開いた。Mod が `exec` で `~/herdr-spike-s6`（git リポジトリ）の中を変更し、`watchFolder` が通知するまでの時間を測った。終了後に Mod・`data/`・検証用ファイルを削除した。

## 結果

| ケース | 通知 | 遅延 | 返ったパス |
|---|---|---|---|
| ファイルへの追記 | あり | 160ms | `file.txt` |
| 一時ファイルに書いて `mv` で置き換え（エディタやエージェントがよく使う方法） | あり | 161ms | `file.txt`, `.tmp-x` |
| 2階層下のサブディレクトリでの変更 | あり | 159ms | `sub/deep/nested.txt` |
| `.gitignore` 対象のディレクトリでの変更 | あり | 163ms | `ignored/i.txt` |
| ファイルの削除 | あり | 165ms | `gone.txt` |
| 変更なし（対照） | なし（2秒でタイムアウト） | - | - |

遅延には `exec` の起動時間が含まれる。

`readTextFile` で読む時間は、1 MiB のファイルでも 0〜2ms、小さいファイルでは 0〜1ms だった。

## 計画への影響

1. **macOS の watch は即時性が十分**（約160ms）。サブディレクトリや ignored も含めて、再帰的に通知される。
2. **watch の通知は、親ディレクトリ以下のすべての変更で届く。** 返ったパスに自分のファイルが含まれる場合（またはルートが返った場合）だけ再読込する。そうしないと、ビルドなどで無関係な再読込が大量に起きる。
3. **ポーリングのコストは小さい**（1 MiB でも約1ms）。ローカルを3秒間隔でポーリングする計画は維持する。watch は即時性を補う役割のまま。
4. 0.1.15 には `cancel()` がない。保留中の watch は変更が起きるまで枠を占有するので、0.1.15 では watch を使わず、ポーリングだけで動かす選択肢もある。次のリリース以降を対象にするので、計画は `cancel()` を前提のままにする。
5. Linux（ignored を監視しない）と Windows は未確認。
